# VISION — Universal Matching Engine («Чорна діра»)

> Цей документ — північна зірка проекту. Він описує **що** ми будуємо і **навіщо**.
> Як будуємо — описують execution-плани (зараз: PLAN v7 v2). Кожна фаза і кожне
> рішення перевіряються питанням: «чи наближає це нас до картини, описаної тут?»

---

## 1. Ідея одним абзацом

Людина пише вільним текстом, що її цікавить. Далі їй більше не потрібно шукати —
**інформація сама приходить до неї**. Система безперервно пропускає через себе
гігабайти інтернету (або локальні набори документів) і віддає людині лише те, що
збігається з її наміром. Кожна дія людини (зірочка, approve, skip) непомітно
уточнює її профіль — система вчиться і з часом віддає все точніше. Результат:
економія часу, сил та енергії на пошуку.

---

## 2. Метафора: ваги

```
   ЛІВА ЧАША                    СИСТЕМА                    ПРАВА ЧАША
   (corpus)                  («чорна діра»,                 (intent)
                          рибальський човен, сито)

  те, що віддає світ ──────► фільтрує ГБ потоку ◄────── те, що хоче людина
  RSS, парсери, API,         embedding + BM25            вільний текст наміру
  web search, файли          + RRF + MMR + rerank        → keywords + вектор
```

- **Ліва чаша** — будь-яке джерело даних. Інтернет (HN, Reddit, RSS, web search,
  парсери) або локальні файли (резюме, контракти, документи). Система може
  приєднатися до чого завгодно — джерела підключаються, а не зашиваються.
  Якщо у сайту немає RSS — юзер просить **AI-конектор**: AI за заздалегідь
  підготовленими інструкціями (playbook) сам будує підключення до цього сайту.
  Власник системи нічого не робить руками — джерела підключають самі юзери.
- **Права чаша** — намір людини. Не зашитий «профіль шукача вакансій», а
  довільний текст: «мене цікавить Rust і системний дизайн», опис вакансії,
  вимоги тендеру, тема для контенту.
- **Система між ними** — universal matching engine. Вона не знає і не повинна
  знати, що лежить на чашах. Вона вміє одне: вимірювати семантичну відповідність
  між лівою і правою чашею та віддавати топ.

**Ключова інверсія:** не людина йде до інформації (гортає стрічки, доки щось
трапиться) — інформація приходить до людини, вже відфільтрована.

## 3. Як це виглядає для людини

### 3.1 Push — система приходить сама
Людина описала намір один раз. За кроном (наприклад, щоранку) система вже
зібрала, відфільтрувала і поклала в inbox усе важливе. Не треба читати новини —
все, що цікавить, **уже прийшло само**.

### 3.2 Pull — миттєвий пошук за тригером
Людина натискає пошук — система негайно проганяє запит по корпусу і віддає
результат тут і зараз. (Зараз: Sync button + `POST /api/search`.)

### 3.3 Багато намірів паралельно
Людина може відкрити **довільну кількість «вкладок»** — окремих намірів на різні
теми (вакансії, Rust-новини, конкуренти, хобі). Кожен намір — окремий профіль зі
своїм inbox і своїм feedback loop.

### 3.4 Система вчиться сама
Approve / Star → профіль зміщується в бік схваленого. Skip → у протилежний бік.
Жодного ручного налаштування — людина просто користується, а точність росте.
(PLAN v7, Phase 2.5: blend векторів +0.15 / +0.10 / −0.05.)

### 3.5 Пам'ять і прогнози (далекий горизонт)
Корпус накопичується. Зі зростанням даних з'являються нові можливості:
- **пошук по історії** — «що писали про X пів року тому», тренд теми в часі;
- **прогнози** — система бачить, як тема набирає обертів, ще до того, як вона
  стала мейнстрімом.

## 4. Два режими корпусу

| | Online (Internet Mode) | Offline (Files Mode) |
|---|---|---|
| Ліва чаша | потік з інтернету (RSS, API, парсери, web search) | завантажені файли (PDF, DOCX, TXT) |
| Права чаша | збережений намір (профіль) | разовий запит або документ-еталон |
| Режим | безперервний (cron) + on-demand | сесійний, ephemeral |
| Приклад | ранковий дайджест за інтересами | ейчар: опис вакансії + пачка резюме → топ-50 → топ-20 |
| Дані | спільний дедуплікований корпус, персональні matches | приватні, ізольовані, тимчасові |

Обидва режими — **той самий engine**. Різниця лише в тому, звідки береться ліва
чаша і як довго живуть дані.

## 5. Вертикалі: одне ядро — незліченна кількість упаковок

Технічно це завжди той самий код. Комерційно — різні продукти (з PLAN v5 + нові):

| Вертикаль | Права чаша | Ліва чаша | Дія |
|---|---|---|---|
| ContentMatch | теми для присутності в мережі | пости, обговорення | draft коментаря — присутність росте майже сама |
| JobMatch | профіль кандидата | дошки вакансій | cover letter |
| RecruitMatch | опис вакансії | пачка резюме | топ кандидатів + email |
| TenderScan | вимоги тендеру | внутрішні документи | gap analysis + draft відповіді |
| NewsRadar | інтереси людини | новинні потоки | ранковий дайджест |
| TrendScout | тема/ринок | історичний корпус | тренди та прогнози |
| … | будь-який намір | будь-який corpus | будь-який action |

Вертикалей не злічити, бо це не фічі — це **підстановки в одну формулу**:
`намір × корпус × дія`. Додати вертикаль = додати source-адаптер та/або action,
ядро не змінюється (архітектура IR + Action Dispatcher з v4 саме про це).

## 6. Стенд Генрі Форда: вимірюваний максимум

Форд не «робив фічі» — він будував стенд, міряв двигун і розширював максимум.
Так само тут: **якість matching — це число, яке ми міряємо постійно**, а не
відчуття.

Принципи:
1. **Золоті датасети** під кожен тип пари: намір↔пости, вакансія↔резюме,
   запит↔новини. З розміченою правильною відповіддю (зародок — seed data з
   5 групами у Phase 2.5: точний збіг, семантичний збіг, частковий, нерелевантний,
   пастка).
2. **Метрики:** precision@k, recall@k, MRR, anti-trap rate, score distribution.
3. **Регресійний прогін:** кожна зміна engine (RRF, MMR, HyDE, contextual
   chunking, нова модель embedding) проганяється по датасетах. Число виросло —
   зміна лишається. Впало — відкочується. Feature flags уже передбачені
   (`USE_RRF`, `MMR_LAMBDA`).
4. **Максимум фіксується** і завжди видно: який він зараз і що його востаннє
   підняло.

Це окремий трек роботи, паралельний фічам — **eval harness**.

## 7. Як ми до цього дійдемо

Фундамент уже існує і задеплоєний (v4 — з користувачами; v5–v7 — universal
core: dynamic profiles, hybrid search, chunking, multi-user, дедуп-корпус).
Шлях — це PLAN v7 + добудова того, чого в ньому ще немає:

| Крок | Що дає для vision | Статус |
|---|---|---|
| Phase 1–2 (v7) | working end-to-end: scheduler → corpus → search → inbox, multi-user | ✅ done |
| Phase 2.5 (v7) | права чаша = вільний текст; feedback loop (система вчиться); дедуп-корпус + user_matches; перший eval (seed data) | 🔜 next |
| Phase 3 (v7) | settings, health — система живе сама, без нагляду | планово |
| Phase 4 (v7) | Files Mode (offline-ваги, RecruitMatch) + dynamic sources (ліва чаша — будь-що: RSS, Tavily/Brave, Firecrawl) | планово |
| **AI-конектор джерел** | сайт без RSS → юзер просить AI, той за готовим playbook сам будує підключення; джерела підключають юзери, не власник | **gap** — у PLAN v7 згаданий як «AI Autonomous» (рівень 4 dynamic sources, фаза 5+); тут фіксуємо як повноцінну ціль |
| **Eval harness** | стенд Форда: золоті датасети + метрики + регресійний прогін | **gap** — оформити як паралельний трек від Phase 2.5 |
| **Multi-intent** | N профілів-«вкладок» на юзера, кожен зі своїм inbox і feedback loop | **gap** — зараз профіль один (active); після Phase 2.5 |
| **Digest / push** | ранковий дайджест: cron уже є, бракує доставки «до людини» (email/notification/digest view) | **gap** — Phase 5+ |
| **History & predictions** | пошук по історії корпусу, тренди, прогнози | **gap** — далекий горизонт, після масштабування корпусу |

Принцип руху: **не переписувати з нуля**. Ядро вже універсальне (рішення
зафіксоване після аудиту v4–v7). Кожна нова потреба — це шар поверх ядра:
новий адаптер, нова вертикаль, новий трек вимірювань.

## 8. Що ми НЕ будуємо (анти-цілі)

- **Не соцмережа і не читалка** — ми не хочемо, щоб людина проводила в системі
  більше часу. Метрика успіху — навпаки, менше часу на пошук.
- **Не автономний бот** — людина завжди в петлі: бачить, чому результат
  релевантний (explainer), затверджує дії, редагує keywords. Система готує —
  людина вирішує.
- **Не «ще один агрегатор всього»** — ми не показуємо потік, ми його **сито**.
  Краще 10 точних результатів, ніж 1000 будь-яких.
- **Не залежність від платного AI** — базовий matching (BM25 + cosine + RRF +
  MMR) завжди безкоштовний і локальний. Платні AI-функції — опційні per-action
  toggles.

---

## 9. Мірило успіху

Людина прокидається, відкриває inbox — і там уже лежить усе, що їй важливо,
по кожному з її намірів. Вона нічого не шукала. Вона нічого не гортала.
Система зробила це за неї — і з кожним днем робить це точніше.
