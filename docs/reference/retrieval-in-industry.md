## 1. Problem

Every ranking decision in this repository was made by taste. ADR-001 chose sequential retrieval for
CPU cost, ADR-003 chose language model reranking because the API was already there, and neither one
cites a system that runs in production anywhere else. When a number needs changing there is nothing
to argue against except an opinion, so the argument is won by whoever writes the commit.

Eleven production search systems were read on 2026-08-13. Their engineering write ups agree with each
other far more than they disagree, and on several points they contradict what this repository does.
That evidence lived only in a chat transcript, which means it would have been lost, and the same
questions would be reopened in two weeks with no better answer than last time.

This document is the single place that evidence lives. Anything in `docs/adr/` that argues about
retrieval cites a row from here instead of restating it.

## 2. Decision

One reference document holding what eleven named production systems actually do, what they agree on,
where they differ, and the six independent decisions those eleven collapse into. It records external
evidence only. It states no plan and changes no behaviour.

Proof of need: not applicable. This document records evidence rather than building anything. The
decision protocol section 2 lists what it governs, and a written record of external systems is not on
that list.

## 4. The eleven systems

| # | System | What is published |
|---|---|---|
| 1 | Anthropic, Contextual Retrieval | A language model prepends 50 to 100 tokens of document level context to every chunk before indexing. Contextual embeddings and contextual BM25 run in parallel, results are fused, then the top 150 are reranked to 20. Measured top 20 retrieval failure: 5.7 percent baseline, 3.7 with context, 2.9 with contextual BM25 added, 1.9 with reranking added |
| 2 | Dropbox, Dash | Lexical retrieval produces candidates, chunking happens at query time rather than at index time so chunks cannot go stale, and a larger embedding model reranks. Target is 95 percent of queries under two seconds. Evaluation is end to end: correctness, completeness, source accuracy |
| 3 | Glean | Hybrid retrieval, a knowledge graph of the organisation, and personalisation by role, department and interaction history. Their stated position is that vectors are weak on exact strings such as error codes and internal acronyms, and that the work is in honest ranking evaluation rather than in the algorithm |
| 4 | Spotify, Natural Language Search | Bi-encoder over a shared query and episode space, served by Vespa approximate nearest neighbour. Positives come from search logs, from query reformulation sessions, and from synthetic queries generated by a fine tuned BART. Negatives are in batch. Dense retrieval was added as one more candidate source next to Elasticsearch, not as a replacement, and a final reranker combines the sources |
| 5 | Instacart | Text retrieval over Postgres GIN and semantic retrieval over FAISS, run in parallel. Recall set size is adapted per query by entropy, `recall_threshold = min(M, max(L, M * query_product_entropy / Q))` at L 500, M 1000 and Q 10, reported as mean converting position better by 1.7 percent and latency lower by 1.5 percent. Reciprocal rank fusion and convex combination were both evaluated, the second as `w1 * lex_score + w2 * sem_score`. Their reciprocal rank fusion is written without a rank constant at all, as the sum of `1/x` and `1/y`. Query understanding was separately rebuilt on language models: retrieve top K converted categories, rerank them with a model, apply a guardrail |
| 6 | DoorDash | gemini-embedding-001 at 256 dimensions through Matryoshka representation learning, with asymmetric retrieval query and retrieval document modes. Their reported result is that input text quality mattered more than model choice, roughly 31 percent from language model generated entity profiles against roughly 6 percent from the model upgrade. Null search rate fell 3.65 percent, conversion rose 0.66 percent, offline precision moved from 68 to 85 percent |
| 7 | Airbnb, embedding based retrieval | Two tower model, listing tower computed offline daily, query tower evaluated online. Negatives are listings the user saw and did not book, not random samples, and random sampling was measured to perform poorly. Inverted file index was chosen over hierarchical navigable small worlds because it handles a high update rate and existing filters better. Euclidean distance produced more balanced clusters than dot product |
| 8 | Pinterest | Two tower learned retrieval, several embeddings per user, conditional retrieval, time decay over the corpus. One model covers queries, pins and products together |
| 9 | LinkedIn | Dual encoder over a shared language model, trained on real interactions by pulling engaged items closer and pushing ignored items away. Embedding version management is treated as a first class problem |
| 10 | Shopify | Classical information retrieval plus machine learning: typo correction, synonyms, faceting, semantic search. Ranking uses gradient boosted trees and neural rankers. Signals include purchases rather than clicks, brand trust, and navigational intent. Performance is tested on every pull request with a 2 percent tolerance |
| 11 | Uber | 1.5 billion vectors of about 400 dimensions on OpenSearch. The published work is infrastructure tuning: merge policy, refresh interval, disabling stored source and doc values, which took the index from 11 TB to 4 TB. Indexing time fell 79 percent, query latency at the 99th percentile fell from 250 ms to 120 ms |

## 5. What they agree on

1. Nobody runs pure vector retrieval. Two candidate sources run in parallel, and dense retrieval is
   added next to lexical retrieval rather than replacing it. Spotify states this explicitly.
2. Retrieval is staged. Candidate generation optimises recall over hundreds or thousands of items,
   reranking optimises precision over tens. The stages are measured separately.
3. A reranker is standard, not an optional extra. In the Anthropic numbers it is the single largest
   improvement of any step.
4. Rank based fusion, or explicit score normalisation, is used instead of adding raw BM25 and cosine
   scores together, because the two scales are not comparable.
5. Query understanding is where the early investment goes: spelling, synonyms, intent, attributes.
6. Indexed text is constructed rather than taken raw. Anthropic prepends context, DoorDash generates
   entity profiles.
7. Ranking blends relevance with freshness, popularity, trust and personalisation.
8. Interaction logs are both the training data and the answer key. Positives and negatives come from
   what people did, and Airbnb measured that the choice of negatives dominates.
9. Offline datasets gate online experiments. A score without its configuration is not a result.

## 5.1 How the field decides a number, and what that says about tuning constants

Added 2026-08-14 17:53 +0200, because the eleven rows above describe architectures and say almost
nothing about method, and method is what a one person project can actually copy.

Offline, the apparatus is three parts: a query set, a search configuration, and a judgment list, per
OpenSearch's own writing on measuring search quality. That is the same apparatus
`docs/plans/evaluation-corpus.md` builds, which is a useful confirmation that the expensive work of
the last two days was the right expensive work.

Online, the apparatus is A/B testing and interleaving. Airbnb published that one interleaving
experiment takes about 6 percent of the traffic of a regular A/B test and about a third of its
duration, a speedup they state as fiftyfold. Offline runs first and is fast and inaccurate, promising
candidates go to the online test.

The consequence for this repository is not a technique to copy but a boundary to admit. There is no
traffic here, so the online half does not exist, and every decision rests on the offline half alone.
That does not make the offline half optional, it makes it the whole instrument, and it is why a
judgment list with a known agreement statistic is worth more here than in a company that can settle an
argument with a live test.

On tuning coefficients, the field's position is the opposite of intuitive and it is published by the
people who ship the algorithm. Elastic writes that the shipped defaults of b 0.75 and k1 1.2 work well
for most corpora and that picking b and k1 is "generally not the first thing to do", pointing instead
at query construction, analysis, synonyms and user feedback.

The rank constant of reciprocal rank fusion is the cleanest example of the same lesson. The value 60
comes from a pilot study in the 2009 paper that introduced the method, and the reported optimum is
flat: anywhere from roughly 20 to 100 barely moves the result. OpenSearch documents 60 as its default.
A number with a flat optimum is not a lever, and time spent moving it is time not spent on the axes
that are known to move results: what text gets indexed, whether candidates are generated in parallel,
and whether a reranker exists.

The provenance of that paragraph is itself uneven and is recorded rather than smoothed. OpenSearch's
default of 60 was read at its own blog. The 2009 paper was not read directly, because two attempts at
its anthology page returned 404, so the pilot study and the flat optimum are held on secondary
authority until the paper is obtained.

## 5.2 How a weight is actually set in a production system

Added 2026-08-15 11:43:15 +0200. Section 5.1 recorded how the field decides a number in general. This
section records the specific case this project is about to face, which is how the fusion weights get
their values, because `docs/eval/beir-axes-a-b.md` section 7.1 swept them and deliberately refused to
move them.

The answer the large systems give is that nobody sets them by hand at all. The weights become
features of a learned ranker. Gradient boosted decision trees trained with a ranking objective,
LambdaMART as implemented in XGBoost and LightGBM, have been the production workhorse for over a
decade and remain in place in 2026, typically as a stage between candidate generation and a neural
reranker. Section 4 of this document already records two of them: Shopify ranks with gradient boosted
trees, and Airbnb, Pinterest and LinkedIn learn the combination end to end instead.

The lexical weight and the dense score stop being a tuning knob and become two features among many,
next to freshness, popularity, trust and interaction history. That is the same list section 5 point 7
recorded, and it explains why no published system quotes an alpha: they do not have one.

What that costs, and why this project cannot copy it yet. A learned ranker needs labelled query and
document pairs in the thousands. This repository has 947 judgments over 50 intents, of which 16 have
any relevant article, recorded in `docs/plans/evaluation-corpus.md` section 12. Training a ranker on
that would fit noise and then be measured on the same noise. Section 8 of this document already
carries the trigger that would unblock it, one hundred logged decisions, and a learned ranker needs
considerably more than that.

What the field does when it cannot train, which is what applies here. Grid search over the weight on
a development split, validated on a held out split with a significance test, and repeated per domain
rather than once globally. Published practice reports optimal weights that differ by subject area,
for example a lexical bias in legal search where exact statutory references matter more than
paraphrase, and the same sources warn that the optimum is corpus specific and drifts, so it is
re-measured rather than set once. Two independent 2026 write ups also give the same starting advice
this project arrived at by measurement: begin with reciprocal rank fusion at a rank constant of 60
and no tuning, and if hybrid does not beat both single branches, stop and find out why before adding
machinery.

The research direction beyond a fixed weight is a weight chosen per query rather than per corpus,
published as dynamic alpha tuning. It is recorded here so that it is not proposed as an axis before
the fixed weight has been measured per vertical, which is the cheaper experiment and is already
scheduled in `docs/plans/retrieval-quality.md` section 13.

The conclusion for this repository, stated so that the next argument about weights starts here.
The shipped 0.4 and 0.6 sit on the flat part of the curve and stay until a per vertical sweep says
otherwise. The sweep is per subject area, reported with intervals, and the peak is not adopted unless
it clears the resolution recorded in `docs/eval/beir-bm25-control.md` section 6.1. A learned ranker is
the correct end state and it is blocked on labels, not on effort.

## 6. Where they differ

| Question | Positions taken |
|---|---|
| Which source produces candidates first | Dropbox and Spotify start lexical and let vectors help. Airbnb and Pinterest start from vectors |
| When chunking happens | Anthropic chunks at index time and enriches with a language model. Dropbox chunks at query time so chunks cannot go stale |
| Nearest neighbour index | Airbnb chose IVF over HNSW for update rate and filters. Spotify uses Vespa, Instacart FAISS, Uber OpenSearch HNSW |
| Where the model comes from | A hosted API, as at DoorDash, against a model trained on the company's own interaction logs, as at Airbnb, Pinterest and LinkedIn |
| Fusion | Reciprocal rank fusion with a fixed constant, against a recall set adapted per query as at Instacart |
| Reranking | A cross encoder in most places. Language model scoring appears more often in offline evaluation than in the online path |

## 7. The six axes

The eleven systems are not eleven alternatives. They are the same staged architecture with different
answers to six independent questions. Reproducing a company means choosing one option on each axis,
which is why the comparison in `docs/plans/retrieval-quality.md` varies one axis at a time instead of
building eleven systems.

| Axis | Options observed | Held by |
|---|---|---|
| A. Candidate generation | Sequential, parallel, lexical first then dense rerank | This repository is sequential today. Everyone else is parallel or lexical first |
| B. Fusion | Reciprocal rank fusion at fixed k, weighted rank fusion, convex combination, recall set adapted per query | Instacart |
| C. Indexed text | Raw chunk, chunk plus its title, chunk plus generated document context | Anthropic, DoorDash |
| D. Query side | Raw query text, extracted keywords, hypothetical document expansion, generated intent expansion | Instacart |
| E. Reranking | None, language model scoring, cross encoder | Anthropic, Dropbox |
| F. Embedding model | English only small model, multilingual small model, multilingual large model, asymmetric query and document modes | DoorDash, LinkedIn |

## 8.1 Public test collections, and how their topics are made

Everything above is about systems. This section is about the measuring instruments the field built,
which were missed on the first pass through this research and are cheaper than anything we can build.

BEIR is a benchmark of retrieval datasets across 9 retrieval tasks, each carrying a corpus, a query
set and human relevance judgments, published on Hugging Face. It exists to measure how a retriever
generalises to a domain it was not tuned on. Its standard metric is nDCG@10, and public leaderboards
mean a number produced here can be compared with numbers produced everywhere else. Among its members
are MS MARCO with hundreds of thousands of human judgments, TREC-COVID, Natural Questions, FiQA,
SciFact, NFCorpus, TREC-NEWS and Robust04.

The count of datasets was written here as 18 on 2026-08-13. The benchmark's own dataset table lists
19 rows, read at 2026-08-14 12:41 +0200, and the paper's title says heterogeneous without a count.
The difference is not important to any decision, and it is corrected rather than argued because a
document that is wrong about a countable thing cannot be trusted about an uncountable one. The table
itself, with the corpus size, query count and availability of each dataset, is reproduced in
`docs/plans/public-benchmark.md` section 4, where it decides which datasets this project uses.

The practical consequence for a one-person project: the expensive half of an evaluation, the human
judgments, already exists for free at a scale no individual can reach.

How TREC develops a topic matters more than it sounds, because it corrects a rule this repository
adopted and got wrong. An assessor arrives with a topic idea and searches the collection first to
estimate how many relevant documents it would have. Topics with too few are revised or discarded. In
the TREC 2023 NeuCLIR track the instruction was explicit: revise the topic when the count falls below
one or rises above twenty, and the final query set keeps topics with at least three relevant
documents.

The line the field actually draws is therefore not "never look at the corpus when choosing a query".
It is "never look at a system's ranking". Checking that an answer exists at all is procedure.
Selecting a query because a particular system retrieved a particular document is contamination.
`docs/plans/evaluation-corpus.md` section 12 records what this cost us.

## 8.2 Retrieval quality is domain specific

BEIR's existence is itself the evidence: a retriever that wins on MS MARCO can lose on SciFact or
NFCorpus, which is why the benchmark is heterogeneous and zero-shot rather than a single corpus. A
configuration is not universally good, it is good on a domain.

This bears directly on packaging this engine per vertical. If quality is domain specific, then the
tuned configuration and the answer key that justified it are per vertical assets, and the engine
itself is the cheap part. `docs/plans/retrieval-quality.md` section 12 carries the open question and
the experiment that would settle it on this project's own data rather than by analogy.

## 8.3 What the field settled on by 2026, and what is now available off the shelf

Added 2026-08-15 11:10:48 +0200, after a second research pass. The eleven systems above were read on
2026-08-13 and describe architectures published between 2022 and 2025. This section records what
changed since, and it changes one thing that matters here: the parts this project is deciding by
measurement are now commodities, while the deciding itself is not.

The stack is no longer contested. Independent 2026 write ups describe the same pipeline as settled:
lexical and dense retrieval in parallel, fused by reciprocal rank fusion, then a cross encoder
reranker. That is the same conclusion section 5 drew from the eleven systems, and it is the shape
`docs/adr/008-parallel-candidate-generation.md` adopted, so this repository is now aligned with the
consensus rather than ahead of or behind it.

Two additions to the same stack are named consistently and neither is measured here. Query rewriting
before retrieval, and an agent that can re-ask the retriever after seeing results. Both belong to
axis D and both stay out of scope until axis D is measured, per
`docs/plans/retrieval-quality.md` section 3.

Learned sparse retrieval, SPLADE, and late interaction, ColBERT, are the two alternatives to the
dense branch that keep being reported as stronger than BM25 on BEIR at a higher index cost. Neither
is an option in this runtime today, which is worth writing down before somebody proposes it as an
axis: both need an index shape `src/eval/bm25.js` and the vector table do not have.

What is available without training anything, verified on the Hub on 2026-08-15 between 11:02 and
11:06 +0200 and recorded with counts in `docs/adr/012-multilingual-embedding-model.md` section 4: a
multilingual embedding model under 500M parameters that runs in this project's existing ONNX runtime,
and a multilingual cross encoder reranker in the same runtime. Axis E was written on the assumption
that reranking means either a language model API or a cross encoder somebody would have to host. It
means neither. It is a package download.

The consequence for this project is a narrowing, not a new plan. Nothing in the retrieval stack is a
differentiator any more, which `docs/product/COMPETITORS.md` section 6 states from the product side.
What remains scarce is the apparatus for deciding which configuration is right for a given subject
area, and this repository has one.
