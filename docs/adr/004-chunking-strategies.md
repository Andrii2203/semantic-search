# ADR-004: Три стратегії chunking

## Проблема
MiniLM-L6-v2 має ліміт 256 токенів (~200 слів). Резюме, контракти, статті — значно довші. Обрізання тексту = втрата інформації = погана якість пошуку.

## Альтернативи
1. Одна фіксована стратегія → не підходить для різних типів документів
2. Тільки semantic → складніше, не завжди є структура
3. Три стратегії з UI перемикачем → гнучко, людина обирає під задачу

## Рішення
Три стратегії за зростанням складності:

### Fixed
- Розбиває по кількості слів з overlap
- Швидко, передбачувано, без залежностей
- Для: пости, коментарі, тексти без структури

### Semantic
- Розбиває по секціях і абзацах
- Chunks відповідають реальним смисловим блокам
- Для: резюме, статті, технічні документи

### Hierarchical
- Summary всього документа + semantic chunks секцій
- Пошук на двох рівнях: загальний зміст + деталі
- Для: довгі контракти, звіти, документація

Уніфікований інтерфейс `chunk(text, strategy, options)` — решта системи не знає яка стратегія активна.

## Trade-offs
+ Людина контролює як індексуються документи
+ Можна порівняти результати між стратегіями
+ Re-chunk endpoint дозволяє змінити стратегію
- Hierarchical потребує Groq API call для summary
- Три стратегії = більше тестів

## Коли переглянути
Якщо з'явиться better-sqlite3 підтримка векторного пошуку або при міграції на pgvector.
